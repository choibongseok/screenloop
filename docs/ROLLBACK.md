# 배포와 되돌리기

## 배포
`scripts/deploy.sh <버전>` 이 서버 jar·웹(Next standalone)·플레이어(정적) 이미지를 `<버전>` 태그로 만들고 `server`, `web`, `player` 를 교체한다.
교체 뒤 헬스 체크(`/actuator/health/readiness`)가 `DEPLOY_WAIT_SEC`(기본 90초) 안에 정상이 되지 않으면 **직전 버전으로 자동으로 되돌리고** 1로 끝난다.
현재 버전은 `.deploy/current`, 직전 버전은 `.deploy/previous` 에 남고, 실행 중인 서버 버전은 `GET /api/version` 으로 확인한다.
PostgreSQL 볼륨은 배포와 되돌리기에서 건드리지 않는다.

## 수동 되돌리기
`scripts/rollback.sh` 가 `.deploy/previous` 버전으로 되돌린다. 이미지가 로컬에 남아 있어 다시 빌드하지 않는다.

## 데이터베이스 변경 규칙
- 변경은 Flyway(`server/src/main/resources/db/migration/V<번호>__<이름>.sql`)로만 한다. 이미 적용된 파일은 고치지 않는다.
- 모든 마이그레이션에는 되돌리는 스크립트 `db/rollback/U<번호>__<이름>.sql` 이 있어야 한다. `MigrationTest` 가 둘이 1:1 인지,
  그리고 실제로 새 번호부터 거꾸로 적용하면 테이블이 모두 사라지고 같은 마이그레이션을 처음부터 다시 올릴 수 있는지 확인한다.
- 되돌리기가 필요한 경우는 옛 버전 서버가 새 스키마에서 돌지 못할 때뿐이다. 새 스키마가 옛 버전과 호환되게 "추가만" 하는 변경(컬럼·테이블 추가)이면
  서버 이미지만 되돌리면 된다. 호환되지 않는 변경은 두 번에 나눠 낸다(먼저 추가, 다음 릴리스에서 제거).
- 데이터를 지우는 되돌리기 스크립트는 운영자가 직접 실행한다. 스크립트가 자동으로 돌리지 않는다.

## 시험
`e2e/tests/z-rollback.spec.ts` 가 실제로 다음을 돌린다: 1.0.0 배포 → 데이터 쓰기 → 1.0.1 배포 → `rollback.sh` 로 1.0.0 복귀(데이터 유지) →
서버가 DB 에 붙지 못하는 잘못된 릴리스(1.0.2) 배포 → 헬스 체크 실패 → 자동으로 1.0.0 복귀(데이터 유지).
